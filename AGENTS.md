- Dashboard/Performance statistics read only from daily_stats and videos (filled by a server-side sync); never from Metricool directly — keeps pages fast and per-client RLS-scoped.
- Frontend calls Metricool only via supabase.functions.invoke('metricool-proxy') — secrets stay server-side.
- Users map to a client via users.client_id; RLS uses current_client_id() — one source of truth for tenant scoping.
- metricool-sync runs from a managed schedule at two UTC times and only proceeds at 07:xx Amsterdam — keeps 07:30 local across DST.
- Selected client lives in ClientContext (admins pick via sidebar, persisted in localStorage; clients use users.client_id); all data pages read clientId from it.
- Roles: user_roles holds 'admin' (HIBE staff, all clients) or 'client' (own client); RLS uses has_role()/current_client_id().
- Every metricool-sync run writes a sync_runs row per client; new clients trigger a backfill from the Klanten page.
- Review item status changes only via the review_action() RPC — it enforces notes/roles and writes review_events history.
- Posts scheduled in Metricool are treated as already approved and are not imported as review items; only HIBE uploads/links go to review.
- Private-bucket media (thumbnails, review-media) uses path clientId/... and is shown via signed URLs; stored IG thumbnails are saved as 'storage:thumbnails/<path>'.
- Library files live in private bucket 'library' at clientId/category/filename with a library_files row; unique per client+category+name so duplicates are rejected.
- Medal levels are computed client-side from videos/daily_stats in src/lib/medals.ts (tested); no stored medal data.
- Medal celebration acknowledgements live in browser storage scoped by client, medal and reached threshold; presentation helpers do not alter metric calculations or existing levels.
- Achievement PNGs are prepared client-side from a fixed-size token-themed composition before download; reuse the existing medal badge and local HIBE logo to keep artwork consistent and avoid private-media requests.
- Two environments: client users use "/" (ClientEnv), admins use "/hibe" (HibeEnv); /hibe/klant/:id reuses the client pages by setting ClientContext.clientId, and in-page links use useBase().
- The client overview composes existing statistics with read-only client-scoped review counts and upcoming content moments; overview selection helpers are tested separately so the Performance calculations and sync remain unchanged.
- The HIBE Socials checklist (/hibe/socials) reads and writes the HIBE Review Hub social_* tables live via the admin-only socials-proxy function — one shared source so both sites always match; never copy that data locally.
- Video's (review board) store files in Cloudflare R2, never Lovable storage: browser uploads multipart via presigned URLs from the r2-video function and plays via short-lived signed GETs — keeps multi-GB files off the backend.
- Video status order and client visibility live in src/lib/videos.ts (tested); clients only change status via video_client_action() and never see internal comments (RLS).
- App frame: pages render their title and single primary action through <PageHeader>/<PrimaryAction> (portals into the fixed top bar) instead of in-page headings — keeps the main button in the same place on every page.
- Media Management (HIBE video's) is step-based: one page per status at /hibe/videos/stap/:slug, overview at /hibe/videos, review at /hibe/videos/:id; trash = video_items.archived_at (no extra status) — keeps the existing statuses and RLS untouched.
- Client-scope routes use :videoId for nested video pages so they never shadow /hibe/klant/:id.
